# Implementation decisions — what Pluton took from the reference studies

> **Historical study (engine note 2026-10-22):** Qwen Code support was removed in the OpenCode-only
> migration. Qwen references below record studied third-party behavior or historical Pluton
> decisions, not current support or setup instructions.

## Purpose

This document records, per decision, what Pluton-Harness **adopted**, **rejected**, or left
**open** after the three Phase 1 reverse-engineering reports (`docs/reverse-engineering/`). Each
item names the idea, the project it came from with a report citation, what Pluton does instead
(ADR references), and an acceptance criterion or concrete future test that would prove Pluton got
it right.

Status vocabulary per item: **decided; runtime behaviour not yet built** (an ADR records it; the
runtime side may not exist yet — as of commit `c53d9c8`, Phase 2 (domain/config/CLI skeleton) and
Phase 3 (durable store, receipts, task-graph admission, `status`/`task`/`graph` CLI) have shipped
with 68 passing tests in 8 files per `docs/ROADMAP.md`, while engines, sandbox and verification
are still future; each item's **Status** line below states what is actually implemented);
**partially decided** (policy exists inside another ADR, no dedicated decision); **open** (no
decision recorded; listed in the final section).

Citations use the report slugs defined in `comparison-matrix.md` (`cc` = cloudroom-core,
`omb-rt` = OpenMausBot runtime, `omb-mcp` = OpenMausBot MCP/workspaces/tests/licensing).

## Adopted (with adaptation)

### A1. Receipts as the unit of dispatch

- **Idea:** one fsynced record captures acceptance + queueing; identical retry returns the same receipt; a conflicting payload under the same id is a hard error.
- **Source:** cloudroom-core (`cc`: `src/session/mod.rs:965-1351`; `src/api/mod.rs:552`; report §13 adapt 1).
- **Pluton:** `request_receipts` row with `request_id`, target kind+id, sha256 of the canonical payload, state, result/error; same id + same payload returns the stored receipt and dispatch is never repeated; same id + different payload → `request_conflict`; IDs generated by default, callers may supply them (ADR-0006, Accepted). Adapted beyond cloudroom: receipts are generic over targets, not only commands to one engine.
- **Acceptance test:** submit the same request id + payload twice → exactly one dispatch event and an identical second response; same id + mutated payload → `request_conflict`; kill the daemon between receipt insert and dispatch → the receipt survives in a named state and no prompt was sent. **Status:** implemented and tested at the store layer (`Store.admitRequest`; `tests/unit/store.test.ts` covers duplicate, conflict, rollback, reopen). Dispatch-side integration arrives with the run loop.

### A2. Fail-closed uncertainty: `failed` vs `unknown_outcome`

- **Idea:** deterministic rejection is safe to retry; anything else (timeout, mid-flight death) is uncertain and must never be blindly resent.
- **Source:** cloudroom-core (`cc`: `src/session/mod.rs:1402-1406`; report §13 adapt 2); OpenMausBot agrees from the other direction (`omb-rt`: `server/runtime/tree.ts:5`).
- **Pluton:** an interrupted or externally-uncertain action ends `unknown_outcome` and is never auto-replayed; only an explicit, policy-checked retry — a new attempt preserving the previous attempt's evidence — may re-dispatch; no exactly-once claims for external side effects (ADR-0006, Accepted).
- **Acceptance test:** kill the daemon mid-engine-prompt; after restart the task is `unknown_outcome`; `pluton task retry` creates a new attempt while the first attempt's evidence remains queryable; assert no automatic second prompt was sent. **Status:** decided, not yet implemented.

### A3. Write-before-act transactions

- **Idea:** commit the decision (row + events + delivery marks) in one transaction **before** the external call; a write failure starts nothing.
- **Source:** OpenMausBot (`omb-rt`: `server/runtime/runtime.ts:364-378`; report §11 adapt 1).
- **Pluton:** every state transition writes state and its event/receipt updates in one `IMMEDIATE` transaction through the store layer; no module mutates tables directly; the daemon is the only writer (ADR-0002 and ADR-0006, Accepted).
- **Acceptance test:** crash-injection at each store write point shows no split commit — a state change is never visible without its event (or vice versa) — and a failed write starts no engine work. **Status:** implemented at the store layer (single `BEGIN IMMEDIATE` transactions; the failing-create rollback test proves no split commit). Crash-injection at every write point is still future.

### A4. Restart reconciliation as a first-class specification

- **Idea:** restart behaviour is specified (rerun once or not; what happens to parked work; what counts as a budget), not left to "the session is still open".
- **Source:** OpenMausBot (`omb-rt`: `server/runtime/tree.ts:5`; `server/runtime/runtime.ts:663-668`; report §11 adapt 5); cloudroom's crash classification is the sibling idea (`cc`: `src/session/mod.rs:302-434`; report §6).
- **Pluton:** at startup the runtime reloads non-terminal work, marks `running` → `unknown_outcome` unless engine-native resume is verified, resumes only what policy allows, and visibly reports unresolved work (ADR-0006, Accepted). Adapted: Pluton defaults to no automatic rerun at all — stricter than both references' rerun-once.
- **Acceptance test:** scripted kill/restart suite: cut turn with no verified resume → zero engine prompts after restart; cut turn with adapter-declared verified resume → exactly one continuation and the native session id is reused; parked (`needs_input`) work reappears without a duplicate wake. **Status:** decided, not yet implemented.

### A5. One wake per child completion

- **Idea:** a completed child produces exactly one wake receipt for its parent, and reports are latched once.
- **Source:** OpenMausBot (`omb-rt`: `server/runtime/runtime.ts:589-609, 626-648`).
- **Pluton:** "a completed child produces exactly one wakeup receipt for its parent; parents consume child results before continuing" (ADR-0006); restated for delegation in ADR-0007 ("a child settling — terminal, or awaiting verification under a gate — wakes each parent channel exactly once; later transitions of the same child are not re-delivered — waiters re-read durable state per slice").
- **Acceptance test:** complete a child task; assert exactly one wake receipt and exactly one parent activation; replaying the child completion event produces no second wake. **Status:** decided, not yet implemented.

### A6. Typed refusals, never thrown into a turn

- **Idea:** refusals are a closed, typed vocabulary; every creation and refusal is an inspectable event; nothing partial is written.
- **Source:** OpenMausBot (`omb-rt`: `server/runtime-coordinator.ts:183-217`; invariant I10).
- **Pluton:** refusals are first-class, inspectable outcomes, never silent truncation; every creation and refusal is an event visible in `pluton logs`/`status` (ADR-0007); transitions outside the table are rejected by `src/domain/state.ts` (ADR-0006).
- **Acceptance test:** attempt cycle, ancestor-delegation, depth and budget violations; assert a typed error code, one refusal event, zero partial rows, and a non-zero CLI exit with `--json` carrying the code. **Status:** partially implemented — admission refusals are typed errors plus `task.admitted`/`request.conflict` events (`src/orchestrator/task-graph.ts`, `src/store/store.ts`); tool-bridge refusals future.

### A7. Capability records tested against the adapter registry

- **Idea:** engine capabilities are declared per engine and tested against the registry so engine additions cannot silently change level/continuation semantics.
- **Source:** OpenMausBot (`omb-rt`: `capabilities.test.ts:13-36, 39-47, 81-104`; report §11 adapt 3); cloudroom's capability gating is the same posture (`cc`: `src/runtime/mod.rs:631-641`).
- **Pluton:** adapters expose a capabilities record; unsupported features return explicit capability errors instead of fabricated behaviour (ADR-0003, Proposed); `EngineCapabilities` is already typed in `src/engines/contract/types.ts` with conservative defaults.
- **Acceptance test:** a conformance test asserts every adapter registered in `src/engines/registry.ts` appears in the capability table and no table row exists without an adapter; adding an adapter without updating the table fails CI. **Status:** implemented — `tests/unit/capability-conformance.test.ts` pins registry ↔ table identity, deep-equals every adapter's `capabilities()`, checks the full capability vocabulary and dev-only labels, and fails when an adapter or capability is added without a deliberate table update.

### A8. Adapter contract isolating protocol encoding

- **Idea:** one interface abstracts every engine over its official structured protocol; raw I/O and lifecycle guarantees live outside the adapter.
- **Source:** cloudroom-core (`cc`: `src/runtime/mod.rs:281-309`; report §7); OpenMausBot's three layers (`omb-rt`: `server/contracts.ts:430-445`).
- **Pluton:** one `EngineAdapter` covering discovery, model listing, auth status (presence only), session start/resume, normalized event stream, interrupt/cancel/close, plus the capabilities record (ADR-0003, Proposed); protocol channel explicitly separate from tmux; newline-delimited JSON-RPC 2.0 client implemented in-repo with bounded buffers, timeouts and redaction (ADR-0003).
- **Acceptance test:** fixture-replay conformance suite per adapter (offline CLI fixtures); an opt-in live test against a real engine; unknown capabilities fail with `CapabilityError`, never a fabricated result. **Status:** decided; contract skeleton exists (`src/engines/contract/types.ts`), adapters not implemented.

### A9. Hard delegation limits plus graph invariants

- **Idea:** bounded recursion with typed refusals — depth, fan-out, counters — plus pre-admission graph validation.
- **Source:** OpenMausBot (`omb-rt`: `server/runtime/types.ts:322-331` default limits; report §6); cloudroom's receipt dedupe prevents the "subagent starts twice" class of bug (`cc`: §3).
- **Pluton:** delegation only through the daemon's restricted tool bridge, validated server-side; `max_team_size` 8, `max_delegation_depth` 3, `max_tasks_per_run` 20, `max_child_tasks_per_task` 5, max concurrent workers 3; no cycles, no ancestor delegation, depth = parent + 1, task count capped transactionally (ADR-0007, Accepted).
- **Acceptance test:** each limit violated in isolation is refused before any provider process is spawned, with exactly one refusal event; parallel proposals cannot overshoot the task-count cap (transactional check). **Status:** implemented for direct admission (all listed limits + cycle/ancestor validators, `tests/unit/task-graph.test.ts`); server-side tool-bridge enforcement future.

### A10. Budgets bound lack of progress; downtime is not charged

- **Idea:** budgets renew on durable progress; the clock excludes daemon downtime so a laptop sleep is not a stall.
- **Source:** OpenMausBot (`omb-rt`: `server/runtime/runtime.ts:650-657`; scenario S26).
- **Pluton:** per-task and per-run wall-clock budgets plus configured caps (ADR-0007); the same principle must hold in the scheduler implementation (adaptation: Pluton expresses the rule in its own budget model rather than OpenMausBot's requests/executions/wakes counters).
- **Acceptance test:** fake-clock test — a run that makes durable progress keeps its window; a stalled run hits its budget; advancing the clock across a simulated daemon outage consumes no budget. **Status:** decided at policy level (ADR-0007); scheduler not implemented.

### A11. Isolated per-task checkouts; the user's tree is read-only

- **Idea:** never operate on the user's working tree; give every unit of work its own checkout and capture diffs as bounded artifacts.
- **Source:** OpenMausBot's shadow-git checkpoints and explicit rejection of per-bot worktrees (`omb-mcp`: `server/checkpoints.ts:106-113`, §6.2 [Inferred]); cloudroom's workspace ownership (`cc`: §3).
- **Pluton:** per-task self-contained clone under `.pluton/workspaces/...` via `git clone --local` (fallback: full local clone), mounted into the Muse container; no `reset`/`clean`/`checkout --force` on the user's clone; integration in a separate Pluton-owned checkout; conflicts stop and preserve both branches (ADR-0005, Proposed; ADR-0009, Accepted).
- **Acceptance test:** run a task end-to-end against a temp project; assert the user's repository is untouched (no new commits, no branch switch, no worktree file outside `.pluton/`), and a forced merge conflict retains both branches plus a `needs_input` follow-up. **Status:** decided, not yet implemented (Phase 5/7).

### A12. Fail-closed parsing of config, policy and scopes

- **Idea:** corrupt or unreadable policy never becomes pass-through or permission; unknown values resolve to the restrictive option.
- **Source:** OpenMausBot (`omb-mcp`: `shared/tool-scope.ts:75-78`, `server/command-allowlist.ts:94-97`, `server/safety-floor.ts:3`); cloudroom's journal fail-closed `JOURNAL_UNWRITABLE` is the storage analogue (`cc`: §6).
- **Pluton:** delegation limits are validated with safe upper bounds at load time (ADR-0007); unknown-newer schemas refuse to open with migration guidance (ADR-0002); any transition outside the table is rejected (ADR-0006); unknown permission names are a config error, never silently ignored (Pluton's own `src/domain/permissions.ts`; the convention matches OpenMausBot's fail-closed parsing).
- **Acceptance test:** invalid, mutated and out-of-range configs refuse to start with the exact field and fix; a damaged persisted state file cannot widen access (deny-all behaviour asserted); an unknown-newer schema version refuses to open. **Status:** partially implemented — config version/path/name refusals and newer-schema DB refusal are implemented and tested; scope/policy parsing arrives with the tool bridge.

### A13. Harness-composed provenance around delegated work

- **Idea:** the opening of a delegated brief is harness-written from stored data, never model text; model text that imitates the marker is escaped; reports are labelled "own account, not verification".
- **Source:** OpenMausBot (`omb-rt`: `server/runtime/envelope.ts:7, 52, 79, 134-165`; report §11 adapt 4).
- **Pluton:** the recorded decision today is narrower — "Manager prose is never authoritative state" and every bridge call is validated server-side (ADR-0007); no ADR yet specifies an envelope format for worker prompts.
- **Acceptance test:** delegation briefs carry a harness-composed provenance block drawn only from stored fields; a brief containing the literal marker is escaped and cannot impersonate the harness; child reports are labelled non-authoritative. **Status:** partially decided; envelope format is an open design item.

## Rejected / avoided

### R1. Re-creating a bespoke durable journal

- **Idea rejected:** copying cloudroom's outbox/guard/sleep/rescue machinery (temp+fsync+rename, cursors, snapshotting).
- **Source:** cloudroom-core (`cc`: `src/session/outbox.rs:181-203`; report §13 avoid 2, [Inferred]).
- **Pluton does instead:** mature storage primitives — `node:sqlite` in WAL mode with `IMMEDIATE` transactions and a single writer (ADR-0002); the journal *semantics* (commit-before-act, fail-closed writes, idempotent retries) are kept as tests, not as hand-rolled fsync code.
- **Acceptance test:** the A3 crash-injection suite must demonstrate no split commits with no fsync/rename code in the repository; review checklist rejects new hand-rolled durability layers. **Status:** implemented as chosen — the store uses SQLite WAL transactions and contains no fsync/rename code; the crash-injection suite (A3) remains future.

### R2. Doc/repo drift and unmaintainable claims

- **Idea rejected:** documentation and ADR references that outlive or contradict the code (README claims PostgreSQL history and 4 harnesses; adapter code ships HTTPS JSONL and 8; ADR references point up to ≥0237 with one ADR shipped).
- **Source:** cloudroom-core (`cc`: §1, §13 avoid 1).
- **Pluton does instead:** README status banner; every statement that was not executed is reported as NOT RUN with a reproducible command; ADRs carry explicit status; `docs/ROADMAP.md` is the single status surface.
- **Acceptance test:** a CI docs check that internal links resolve and that status claims link to a test or carry the NOT RUN convention (mechanism not yet defined in an ADR — see O5). **Status:** avoided by convention; enforcement mechanism open.

### R3. Vestigial states with no producer

- **Idea rejected:** publishing state machines whose states have no producer or no defined exit (cloudroom ships `waiting_for_files` with no producer in the snapshot; `rewinding`/`suspended` exist for private features).
- **Source:** cloudroom-core (`cc`: §4, §13 avoid 3).
- **Pluton does instead:** one tested state machine in `src/domain/state.ts` where any transition outside the table is rejected (ADR-0006); the skeleton table is the full intended set.
- **Acceptance test:** state-coverage test — every declared task/run/engine/sandbox state has at least one test that enters and leaves it, or the state is removed before release. **Status:** implemented — `tests/unit/state-coverage.test.ts` builds the task/run graphs from the exported transition functions, checks incoming/outgoing coverage and terminal consistency, and exercises every sandbox state through `setSandboxState`. The declared-but-unused engine-process vocabulary was removed from `src/domain/state.ts`; the test's vocabulary-inventory ratchet fails if a new `*_STATES` export is added without coverage.

### R4. A monolithic host above a clean runtime

- **Idea rejected:** a single god module holding goal runs, seats, cards and watchdogs beside a clean runtime (OpenMausBot's `server/index.ts` is ~17k lines and the contract lists three "what remains" leaks).
- **Source:** OpenMausBot (`omb-rt`: §11 avoid 1; `omb-mcp`: §11.2 item 3).
- **Pluton does instead:** enforced module directories mirroring the architecture (`domain/ runtime/ persistence/ engines/ orchestration/ sandbox/ terminal/ workspace/ tools/ verification/ config/ cli/`), with boundaries enforced by dependency-direction unit tests (ADR-0001, Accepted).
- **Acceptance test:** the dependency-direction unit test fails when a forbidden edge is added (e.g. `domain/` importing `cli/`); module layout review at every phase gate. **Status:** implemented — `tests/unit/module-boundaries.test.ts` enforces dependency direction for `domain/`, `util/`, `config/`, `store/`, `workspace/`, keeps presentation modules out of infrastructure/transport, keeps engine adapters below orchestration, and lets only `cli/` compose the server. The two existing non-CLI imports of `cli/` (`server/routes.ts`, `tools/operator-catalog.ts`) are explicit tracked-debt allowlist entries; a new edge fails, and a stale entry fails too.

### R5. Memory-only state beside durable state

- **Idea rejected:** keeping behaviour-relevant state in plain maps (OpenMausBot's `parkedSeats` silently loses seat choice across restarts).
- **Source:** OpenMausBot (`omb-rt`: `server/index.ts:2156`; §11 avoid 2).
- **Pluton does instead:** "all task truth is readable from SQLite; the CLI never invents state" (ADR-0006); the daemon is the only writer (ADR-0006 consequences).
- **Acceptance test:** kill the daemon mid-run; `pluton status --json` after restart accounts for every pre-kill task in a named durable state; review rule forbids module-level mutable task-state singletons. **Status:** implemented at the data layer — task/run truth lives only in SQLite (no memory-only mirrors). The daemon kill/restart test arrives with the run loop.

### R6. Writing into other tools' global configuration

- **Idea rejected:** drivers that write or merge engine global config for their own purposes (OpenMausBot's OpenCode driver writes `opencode.json` for model injection and merges the user's permission rules).
- **Source:** OpenMausBot (`omb-rt`: `server/drivers/acp/opencode-go.ts:447-459, 604-678`; §11 avoid 4).
- **Pluton does instead:** per-Muse engine home plus engine-specific config-dir environment variables and a minimal env allowlist; the documented flow is a fresh login per Muse, never copying or editing the user's own engine config (ADR-0008, Accepted).
- **Acceptance test:** filesystem diff around an engine launch with a temporary HOME — no writes outside the Muse engine home and `.pluton/`; assert no user config file is created or modified. **Status:** decided, not yet implemented.

### R7. Inheriting a default-permissive approval mode

- **Idea rejected:** defaulting new agents to the most permissive engine mode (OpenMausBot's `DEFAULT_APPROVAL_MODE = "full"`); the report itself flags this as wrong for a local-first tool.
- **Source:** OpenMausBot (`omb-mcp`: `shared/approval-mode.ts:47-51`; §11.2 item 1).
- **Pluton does instead (partial):** capability-expanding creations require an approval record (ADR-0007); protected paths require approval before integration (ADR-0009); a `needs_approval` state exists (ADR-0006). There is no dedicated approval-mode decision yet — Pluton must resolve unknown/absent policy fail-closed and must not define a "full access" equivalent by default.
- **Acceptance test:** once a mode model exists — a new Muse starts in a reviewable mode; an unknown or missing mode resolves to the most restrictive agent-run policy; only an explicit, recorded grant elevates. **Status:** avoided by omission today; dedicated decision open (see O2).

### R8. Shell-text classifiers sold as a security boundary

- **Idea rejected:** an independent shell-command analyzer as containment (OpenMausBot's safety floor is off by default, inert on Windows servers, cannot see engines that never ask, and its own doc lists degrade cases).
- **Source:** OpenMausBot (`omb-mcp`: `docs/verification/safety-floor.md:85-137`; §11.2 item 2).
- **Pluton does instead:** OS-level containment is the boundary — containers with cap-drop, no-new-privileges, resource limits, mount/env allowlists (ADR-0004); deny-lists would be secondary defense only, and host execution with deny-lists is explicitly rejected (ADR-0004 alternatives).
- **Acceptance test:** Phase 8 security review verifies no code path represents command-string analysis as containment; Docker-unavailable path fails closed with the exact fix message (ADR-0004). **Status:** decided, not yet implemented.

### R9. Transcript-replay engines as a primary target

- **Idea rejected:** making stateless chat-completions engines a first-class engine family in the core contract (OpenMausBot needs delivered-prefix dedupe and a 64-round agentic cap for them).
- **Source:** OpenMausBot (`omb-rt`: `server/drivers/openai-chat.ts:140, 480-502`; §11 avoid 5).
- **Pluton does instead:** the MVP targets session-native structured protocols — OpenCode via ACP first (ADR-0003); if a stateless engine is ever added, its loop cap lives in that adapter's capability record and never leaks into core state semantics.
- **Acceptance test:** if/when such an adapter ships, the conformance suite fails unless the adapter declares its step cap as an explicit capability; the core state machine is unchanged by its presence. **Status:** deferred by scope; decision recorded here, not in an ADR.

### R10. Duplicated owners of the same behaviour

- **Idea rejected:** two stall authorities and two loop-guard concepts owning the same decision (OpenMausBot's runtime `turnStallMs` is set to 24 h precisely so the host watchdog stays the real detector).
- **Source:** OpenMausBot (`omb-rt`: §11 avoid 3; `server/runtime-coordinator.ts:26, 119`).
- **Pluton does instead:** one tested state machine in `src/domain/state.ts` is the only place transitions are defined (ADR-0006, module header states the rule); one scheduler owns admission.
- **Acceptance test:** boundary test asserts transitions exist only in `domain/state.ts`; review rejects a second watchdog or transition owner. **Status:** rule decided; test not implemented.

## Still open

### O1. Machine streaming/replay protocol

- **Question:** should Pluton expose an event stream with reconnect replay (both references use SSE with `Last-Event-ID`; `cc`: §10; `omb-mcp`: `server/sse-fanout.ts:11-38`), or keep everything behind `pluton logs`/`status --json`?
- **Closing action:** an ADR defining the surface (if any), plus a reconnect/replay test (disconnect a client, reconnect, assert no gaps and no duplicates).
- **Status:** decided and implemented for the query/replay path — ADR-0017 defines the seq-cursor contract (`src/store/query.ts`; CLI `pluton logs [run]`), keeps SSE as a live tail with durable-log recovery, and is covered by `tests/unit/log-query.test.ts` and `tests/integration/cli-logs.test.ts` (pagination, reconnect, filters, typed failures). Server-side historical SSE replay/generations remain rejected.

### O2. Approval model and default mode

- **Question:** what is Pluton's approval vocabulary and default? OpenMausBot's five-mode enum (`omb-mcp`: `shared/approval-mode.ts:5-7`) is prior art, but its default (`full`) is explicitly rejected (R7).
- **Closing action:** a dedicated ADR (mode set, default, fail-closed resolution, elevation journal) plus tests: unknown → restrictive; unconfirmed grant → restrictive; a typed line never answers a card (`omb-mcp`: `docs/runtime-contract.md:39`).
- **Status:** open; approvals exist only as scattered rules in ADR-0006/0007/0009.

### O3. Engine-native resume verification

- **Question:** which engine capabilities count as proof that a native session can be resumed (cloudroom persists native identity and tests reattachment — `cc`: `src/session/mod.rs:1954-2219`; OpenMausBot has per-driver startup-recovery paths — `omb-rt`: `server/drivers/claude.ts:1835-1888`)?
- **Closing action:** ADR-0003's Phase 4 addendum must name the verification probe per engine; a fixture test "resume reattaches and continues the native rollout" for the first adapter, live opt-in; `resumeSession` false/absent → no resume claims.
- **Status:** open; ADR-0003 (Proposed) schedules the addendum but does not yet name the probe.

### O4. Tool-bridge gating design

- **Question:** in-process gate or separate gate process; scope language and spill/budget behaviour; where credentials and policy live.
- **Prior art:** OpenMausBot's gate process validates policy before spawning anything, filters calls and catalogs, trims and spills oversized results, and fails closed on corrupt policy (`omb-mcp`: `server/mcp-gate.ts:184-186, 246-301`).
- **Closing action:** a design note plus tests: corrupt policy never becomes pass-through; deny wins; every bridge call is authorized server-side (ADR-0007); redaction of diagnostics.
- **Status:** open; ADR-0001 defers `@modelcontextprotocol/sdk` to implementation time; ROADMAP Phase 6 not started.
- **Engine wiring evidence:** `docs/reverse-engineering/engine-mcp-integration.md` (2026-10-16) — live-verified MCP configuration, tool naming, and approval gates for OpenCode v2.0.30 and Qwen Code 0.25.2.

### O5. Doc-drift enforcement mechanism

- **Question:** how to make R2 mechanical rather than aspirational.
- **Prior art:** OpenMausBot's expected-capability table and source-extracted constants make drift a test failure (`omb-rt`: `capabilities.test.ts:39-47, 73-78`); its doc line numbers are still stale, showing that mechanics + link checks are both needed.
- **Closing action:** a CI check (dead internal links; status claims must link to tests or carry the NOT RUN convention) recorded in an ADR or development doc.
- **Status:** implemented for dead relative links — `scripts/verify-docs.mjs` walks README, THIRD_PARTY_NOTICES and `docs/**/*.md`, reports every unresolved relative target, runs as `npm run verify:docs`, and is invoked by `scripts/release-check.mjs`; `tests/unit/doc-links.test.ts` proves the repo passes and a fixture with a dead link fails by name. The status-claim / "NOT RUN" half of the convention remains review discipline rather than tooling.

### O6. Outward-effect probe (only if auto-rerun is ever adopted)

- **Question:** OpenMausBot refuses to rerun a cut turn that already acted outward (`omb-rt`: `server/runtime/runtime.ts:663-668`), and its own report notes that absent probe support biases toward rerunning, which can duplicate outward actions (`omb-mcp`: §12 open question 3). Pluton currently never auto-reruns, so no probe is needed.
- **Closing action:** either record "Pluton never auto-reruns; no probe" explicitly as an ADR-0006 clarification, or, if a future engine-native resume path wants automatic continuation, specify the outward check and test it (cut turn that performed an external effect is not re-executed).
- **Status:** open; neither decision recorded.

### O7. Windows containment verification

- **Question:** how much of ADR-0004's container policy is proven on the supported host, given the Docker daemon was stopped at recon time (and cloudroom's containment was read-verified, never executed — `cc`: §2).
- **Closing action:** run the Phase 5 Docker-dependent tests with the daemon running, store output and mark anything still unexecuted NOT RUN; verify the dev-only `local-process` sandbox cannot be selected for team runs without `sandbox.local_process_acknowledged: true` (ADR-0004).
- **Status:** open; environment-dependent.

### O8. Outbound license decision

- **Question:** Pluton's own license is deliberately undecided (`license: "UNLICENSED"`, private repo; ADR-0011 records the owner's call; Apache-2.0 is the named candidate).
- **Closing action:** owner decision recorded as an ADR amendment; `THIRD_PARTY_NOTICES.md` updated. This does not block implementation but blocks any distribution decision.
- **Status:** open by explicit owner choice (ADR-0011).
