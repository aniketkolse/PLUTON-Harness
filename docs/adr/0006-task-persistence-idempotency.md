# ADR-0006 — Task-state persistence and idempotency semantics

- Status: Accepted (2026-10-16)

## Context

Multi-agent orchestration fails badly when retries double-dispatch work, when "completed" is
decided by an LLM's prose, or when a crash leaves ambiguous half-states. The master prompt
mandates durable request receipts and explicit uncertainty states.

## Decision

- **State machine** (single tested module in `src/domain/state.ts`):
  `created → queued → admitted → running → { waiting_for_children, needs_input, needs_approval,
  verifying, completed, failed, cancelled, interrupted, unknown_outcome }`.
  Terminal states never transition further. Any transition outside the table is rejected.
- **Receipts:** a `request_receipts` row records `request_id`, target kind+id, a sha256 of the
  canonical JSON payload, state, and the recorded result/error. Same request ID + same payload →
  the stored receipt is returned and **dispatch is never repeated**. Same ID + different payload
  → `request_conflict` error. Request IDs are generated by default; callers may supply them.
- **Transactional writes:** a state transition and its event append happen in one SQLite
  transaction; a crash can lose the *pending* operation, never split it.
- **Events:** append-only, monotonically sequenced (`events.id INTEGER PRIMARY KEY
  AUTOINCREMENT`), typed, bounded and redacted payloads; every retry, refusal, cancellation,
  approval and state change is inspectable here.
- **Scheduling:** per-Muse serialization in MVP (a Muse never overlaps its own tasks);
  independent Muses run in parallel up to configured limits; dependency edges gate admission;
  cycles and ancestor-delegation rejected at graph validation time.
- **Uncertainty:** an interrupted or externally-uncertain action ends `unknown_outcome` and is
  **never auto-replayed**; only an explicit retry (policy-checked, producing a new attempt and
  preserving the previous attempt's evidence) may re-dispatch. No exactly-once claims for
  external side effects.
- **Crash recovery:** at startup the runtime reloads non-terminal work, marks states that can no
  longer be trusted (`running` → `unknown_outcome` unless engine-native resume is verified),
  and resumes only what policy allows; unresolved work is visibly reported.
- **Wakeups:** a completed child produces exactly one wakeup receipt for its parent; parents
  consume child results before continuing.

## Consequences

- All task truth is readable from SQLite; the CLI never invents state.
- The daemon is the only writer; CLI commands go through the runtime API.
- Deterministic tests can drive the whole machine with a mock engine before any real model runs.

## Alternatives considered

- State in memory + event log replay — rejected: replay semantics around external effects are
  precisely what the prompt forbids guessing.
- One boolean per task — rejected: collapses engine, sandbox and verification states that must
  stay distinguishable.

## Evidence

- Prompt §5 semantics; OpenMausBot/Cloudroom patterns validated by the Phase 1 reverse-engineering
  reports (`docs/reverse-engineering/`).
