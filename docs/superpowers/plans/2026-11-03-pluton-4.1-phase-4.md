# PLUTON 4.1 Phase 4: Persistent Build Mode & Dynamic Planning Refinement Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Build a persistent project session: the first Build establishes the workspace and operator-defined name, later Builds reuse it without a repeat confirmation, and every manager receives bounded durable lineage so it refines the existing plan instead of recreating completed work.

**Architecture:** A `project_sessions` row is anchored per canonical project and linked from `runs.project_session_id`. The API and CLI create runs through the same session-aware path and increment a durable build counter. The supervisor reads prior runs/tasks for the session and injects a capped refinement section into `buildManagerPrompt`. Rename updates `pluton.yaml`, SQLite, and the registry atomically, preserving the root path. The SPA skips the first-build panel once `buildCount > 0`.

**Tech Stack:** TypeScript, Node.js 24 (`node:fs`, `node:sqlite`), SQLite3, YAML document API, vanilla HTML/CSS/JS (embedded SPA).

**Spec:** `docs/superpowers/specs/2026-11-03-persistent-build-mode-design.md`

## Global Constraints

- **SQLite authority:** sessions, build counts, and run lineage are durable rows; no shadow in-memory state.
- **Additive migration:** the new schema version only adds a table, a nullable column, and an index.
- **Path immutability:** rename never changes `projects.root_path` or the session workspace.
- **Approval preservation:** removing the repeat Build panel must not bypass tool/shell/file approvals.
- **Bounded prompts:** lineage text is capped with an explicit truncation marker.
- **Phase 3 invariants:** intra-project busy protection (409) and cross-project concurrency remain intact.
- **Contract compatibility:** `scripts/verify-assets.mjs` required IDs are expanded, never weakened.

## Review Focus

1. **Restart reuse:** Build → Build → restart → Build must reuse the same session and workspace.
2. **Rename atomicity:** an invalid name or invalid config must leave all three stores unchanged.
3. **Lineage honesty:** prior build summaries reflect durable run/task state, never fabricated success.
4. **No duplicate work:** the refinement instruction must explicitly forbid recreating completed tasks.
5. **First-vs-later Build:** only the first build in a project shows the panel; later builds dispatch directly.
