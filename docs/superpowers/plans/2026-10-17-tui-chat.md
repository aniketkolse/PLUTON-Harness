# Pluton Interactive Chat TUI — "Operator Muse" — Design & Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Committed 2026-10-17** as the execution plan for the chat TUI slice (written in plan mode, executed inline). Task 0 commits this file together with ADR-0012.

**Goal:** Typing `pluton` in a project (TTY) or `pluton chat [muse]` opens an interactive chat with one Muse — the **operator's proxy ("us")**. Streaming replies, tool calls as they happen, a live status line, slash commands, session persistence with `--continue`/`--resume`, an approvals inbox you decide inline, and an **operator tool bridge** so the Muse can actually inspect state and start supervised runs from the conversation. Zero new runtime dependencies; inline scrolling renderer (Claude Code "classic" model), no alt-screen in v1.

**Why these choices (research + codebase evidence):**

- **pi & Claude Code inventory** (research agent, 2026-10-17): both are inline-first chat UIs with a streaming transcript, a short live bottom region, collapsible tool output (`Ctrl+O`), queued messages while busy, permission prompts with Yes/No/always, status line with usage, session resume, and slash/`@` input affordances. pi additionally has named rebindable actions, role-based theme tokens, and a fullscreen/scrollback duality. Both deliberately support inline mode as the default shape.
- **Stack matrix** (research agent, 2026-10-17): Ink 8 = Claude Code's stack, ~60 packages/~15 MB, JSX needs a compile step that would break this repo's "no build step on Node 24" property; pi-tui = young, pi-specific; **zero-dep hand-rolled inline renderer** = ~600–1000 LOC, fits this repo's DNA (hand-rolled ACP client, MCP server, HTTP transport; 3 deps total: commander/yaml/zod) and keeps `bin/pluton.js` running TS directly. Decision: zero-dep, inline-first; the renderer is a pure-function seam (`state → frame`) so a later Ink swap stays contained if ever wanted.
- **Codebase map** (research agent, 2026-10-17): the engine session API already streams everything the TUI needs (`text`/`tool`/`usage`/`approval_request`/`result` events through `sendPrompt()`); the supervisor currently discards most of it. Three real gaps to solve: (1) `PlutonToolBridge` requires an existing run row — chat is run-less; (2) no chat persistence — needs migration v3; (3) Pluton approvals are only decidable from the CLI — the TUI should surface them. Engine-level permission prompts stay fail-closed in v1 (the async handler contract is a follow-up), surfaced honestly in the transcript.

**Design calls made in this plan (review these):**

1. **Entry points.** `pluton chat [muse]` (top-level) and `pluton muse chat <muse>` (the README-promised alias) are the same flow; bare `pluton` opens chat **only when stdin+stdout are TTYs and a Pluton project exists** — otherwise the current help behavior is unchanged. `--json` never starts the engine: it resolves the chat plan (muse, mode, container, session) and prints one envelope (mirrors `attach`).
2. **Rendering stack.** Zero new runtime dependencies. Pure modules (`width`/`theme`/`render`/`state`/`editor`/`keys`) + one I/O module (`terminal.ts`) that owns raw mode, keypress events, resize, and the live-region redraw. Committed transcript lines are plain writes (append-only scrollback); only the bottom region (status + streaming text + input) is redrawn by cursor-up + clear-down. No alt-screen, no scroll regions (DECSTBM is unevenly emulated by ConPTY), no `ESC[6n` (ConPTY latency — ADR-0010 Windows boundary).
3. **Who "us" is.** The default chat Muse is the project's supervisor-role Muse (the same resolution `pluton run` uses); `pluton chat <muse>` targets any enabled Muse. The session prompt = a built-in operator preamble (concise, tool-first) + the Muse's `instructionsFile` if present (loaded the same way `RunSupervisor.instructionsFor` does). No new config surface in v1.
4. **Operator bridge scope.** `PlutonToolBridgeOptions.runId` becomes optional: **absent = operator scope** (no run row required), exposing a small operator catalog only. Run scope is unchanged (existing catalog only). Per-call permission checks and audit events stay identical (`run_id` null for operator calls). The operator catalog (v1): `project.status`, `run.list`, `run.get`, `run.start`, `approvals.list` with new permissions of the same names (`run.inspect` for `run.get`); supervisor role defaults gain all five.
5. **`run.start` drives in-process.** No detached child process: the chat process creates the run (same admission/receipt path as `pluton run`) and hosts its `RunSupervisor` in the background, exactly like `pluton run` hosts it in the foreground. One chat-started run at a time (guard: a second `run.start` returns a typed tool error). Exiting chat mid-run stops the supervisor — the same semantics as Ctrl+C on `pluton run` today (documented, warned on exit). Live progress is rendered by polling the durable event cursor (`store.eventsSince`), which also works for approvals and status.
6. **Chat persistence.** Migration v3 adds `chat_sessions` + `chat_messages` (new tables — the `events` table's 8 KiB payload cap and lack of session grouping make it a poor transcript store). `--continue` resumes the latest session for the Muse; `--resume <id>` an explicit one. Native resume tokens are passed when the engine supports them (opencode: yes); otherwise the stored transcript is re-rendered and a fresh engine session starts (honest, documented — qwen degrades).
7. **Approvals.** Pluton approvals are interactive in v1: status line shows the pending count, `/approvals` lists, `/approve <ref>`/`/deny <ref>` decide through the existing `decideApproval` code (with `chat-<session>-<n>` request ids). New pending approvals appear as transcript notices on the poll tick. Engine permission prompts (`session/request_permission`) stay fail-closed exactly as today and are surfaced as transcript lines; the async interactive handler contract is an explicit follow-up.
8. **Layout (v1, inline).** Startup header (project/muse/model/session), transcript (user `›`, assistant streaming, tool lines `⏺ name … ok|failed` toggled by `Ctrl+O`, notices `·`), status line (muse · engine/model · run state · approvals · token usage), input line (`› ` multiline, cursor movement, history, >10-line pastes collapse to `[paste #N +M lines]`). Keys: Enter send / queue-when-busy, Ctrl+J or Shift+Enter newline, Esc interrupt, Ctrl+C clear→interrupt→(double) exit, Ctrl+D exit, Ctrl+O tools, Ctrl+L redraw, Up/Down history, readline edits (Ctrl+A/E/U/K/W). Slash: `/help`, `/status`, `/runs`, `/run <goal>`, `/approvals`, `/approve <ref>`, `/deny <ref>`, `/new`, `/quit`.
9. **Theme.** Minimal role-based SGR tokens; `NO_COLOR` and non-color terminals render plain. No custom theme files in v1.
10. **Honest limits.** This harness has no real TTY: the live leg proves a full conversation + `run.start` + approvals against a real engine through the injectable `ChatIo` seam (scripted frames recorded in `docs/smoke-live-run.md`); the real raw-mode terminal leg is recorded NOT RUN with instructions for the operator (same pattern as `attach`). Tool output content and engine "thinking" are not surfaced (the normalizer drops them) — follow-up.

## Global Constraints

- TypeScript strict, ESM, Node ≥ 24; **no new runtime dependencies** (renderer hand-rolled); argv arrays only.
- Secrets never in argv, DB rows, events, logs, or artifacts (ADR-0008). Bridge bearer tokens ride only in the engine session params.
- `--json` (or `PLUTON_JSON=1`) → stdout is exactly one envelope via `runCommand`/`emitOk`; diagnostics on stderr; typed `PlutonError` subclasses with stable codes. The interactive loop bypasses the envelope (the `attach` precedent).
- Never touch the user's repository tree from chat; the operator Muse's project view is read-only (same mount policy as the manager in `run`).
- Committed scrollback lines are never re-written; the live region is exactly the tracked row count (byte-level tests pin this).
- Tests deterministic (fake timers for throttle/polling); live/Docker checks opt-in, executed with recorded evidence or reported NOT RUN with exact commands.
- `npm run check` (typecheck + full suite) green before every commit; incremental conventional commits.

## Review Focus

Failure modes the tests must pin (each gets a test in the owning task):

1. **Scope isolation.** An operator-scoped bridge can never call run-scoped tools (and vice versa) even when the Muse holds both permissions — `tool.denied` audit with `reason: 'unknown_tool'`; a Muse lacking an operator permission gets `policy_denied` and a `tool.denied` audit.
2. **`run.start` guard.** While a chat-started run is active, a second `run.start` returns a typed tool error (never a second run); after completion a new one is allowed; a duplicate `--request-id` retry returns the same run id without re-driving.
3. **Redraw integrity.** Commits only happen with a cleared live region; the byte sequence for redraw is exactly `up(rows-1) + \r + ESC[J + frame + \r + up(n) + [ESC[<col>C]` (asserted with a fake stdout); resize re-renders the live region without touching committed lines.
4. **Interrupt honesty.** Esc during a turn → `session.interrupt()` → stream ends `cancelled`/`unknown` → the assistant block is finalized marked `interrupted`, persisted with `meta.interrupted: true`; never a fabricated success.
5. **Resume honesty.** `--resume` of an unknown/foreign session id fails loudly (`NotFoundError`/`ValidationError`); a stored `resumeToken` is passed only to engines whose `capabilities().resumeSession` is true; stored native ids are updated after every `startSession`.
6. **Non-TTY / `--json` safety.** `pluton chat` without a TTY (and without `--json`) fails with a typed error naming the fix; `--json` never constructs an adapter, spawns a container, or starts the HTTP bridge.
7. **Persistence caps.** A >32 000-char message persists truncated with an explicit marker; `seq` is strictly monotonic per session under concurrent appends (two appends in one tick → 1,2).

**Interfaces:**
```ts
export interface ChatIo {
  readonly isTty: boolean
  size(): { columns: number; rows: number }
  /** Append finalized lines to scrollback. Requires an empty live region (asserted). */
  commit(text: string): void
  /** Replace the live region. `frame.cursor` parks the terminal cursor inside it. */
  redraw(frame: { lines: string[]; cursor: { row: number; col: number } }): void
  onKey(handler: (input: string, key: Key) => void): void
  onResize(handler: () => void): void
  start(): void   // raw mode, bracketed paste on, keypress + resize wiring
  stop(): void    // restore stdin/stdout (bracketed paste off, raw mode off, cursor shown)
}
export class TerminalHost implements ChatIo {
  constructor(opts?: { stdin?: NodeJS.ReadStream; stdout?: NodeJS.WriteStream; throttleMs?: number /* default 33 */ })
}
```
- Redraw byte algorithm (pin exactly in tests): if `liveRows > 0` → `ESC[<liveRows-1>A` when > 1 else `\r`; then `\r` + `ESC[J`; write `lines.join('\n')` (no trailing newline); park: `\r` + (`ESC[<n>A` when `cursor.row < lines.length-1`) + (`ESC[<cursor.col>C` when col > 0); set `liveRows = lines.length`.

- Sequences allowed: `A`, `C`, `J`, `K` + bracketed paste `ESC[?2004h/l`. **Never** `ESC[6n`, never DECSTBM. On `stop()`: disable bracketed paste, raw mode off, trailing redraw flush.
