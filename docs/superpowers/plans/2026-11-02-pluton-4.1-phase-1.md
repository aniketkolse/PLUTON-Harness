# PLUTON 4.1 — Phase 1: Provider adapter architecture

Spec: recovered PLUTON 4.1 specification, §K Phase 1 (provider adapter architecture).
Status: implementation plan (inline execution).

## Global constraints

- SQLite remains the authority; no schema migration in this phase.
- No secret ever reaches YAML, SQLite, events, logs, argv, SSE, or errors.
- No hardcoded model ids and no provider-specific fallback lists.
- Unsupported capabilities throw `CapabilityError`; they are never faked.
- Mock stays `devOnly`; production discovery and selection exclude it.
- Provider-specific protocol code lives only under `src/engines/openai-compatible/`.
- Existing behaviour and tests must keep passing.

## Task 1 — Provider metadata and credential store

Files: `src/providers/types.ts`, `src/providers/store.ts`,
`tests/unit/provider-store.test.ts`.

Produces:

- `ProviderConfig` (id, engine, display_name, base_url, auth, models_path,
  chat_path, headers, timeout_ms).
- `loadProviderRegistry(rootDir)`, `getProvider`, `saveProvider`,
  `removeProvider`, `resolveProviderForEngine`.
- `writeProviderCredential`, `readProviderCredential`,
  `hasProviderCredential`, `removeProviderCredential`.
- Credential files under `.pluton/provider-homes/<id>/credential.json` with
  directory mode `0700`, file mode `0600`, plus best-effort Windows ACLs.
- `providers.json` contains metadata only, never a key.

Tests: validation, atomic metadata, no secret in metadata, credential
round-trip/removal, permissions on POSIX, ambiguous provider error,
missing/malformed credential errors without leaking contents.

## Task 2 — OpenAI-compatible HTTP client and MCP client

Files: `src/engines/openai-compatible/client.ts`,
`src/engines/openai-compatible/mcp-client.ts`,
`tests/unit/openai-compatible-client.test.ts`.

Produces:

- Configurable base URL/auth header; no provider URL or model id hardcoded.
- `listModels` parsing OpenAI-compatible `{ data: [...] }` without renaming ids.
- HTTP error mapping: 401/403 -> `EngineAuthMissingError`, 429/5xx/other
  -> `EngineProtocolError` with status/details and redacted body.
- SSE chat streaming parser (`data:` frames, `[DONE]`, non-stream JSON fallback).
- MCP JSON-RPC HTTP client: `initialize`, `tools/list`, `tools/call`.

Tests: auth header styles, exact id preservation, malformed payloads,
401 redaction, SSE split frames, MCP handshake and tool result mapping.

## Task 3 — OpenAI-compatible adapter

Files: `src/engines/openai-compatible/adapter.ts`,
`tests/unit/openai-compatible-adapter.test.ts`.

Produces:

- Registered kind `openai-compatible`, `devOnly: false`.
- Honest capabilities: interrupt, usage, modelList, mcpServers true;
  resumeSession, approvals, sessionExport false.
- `discover`, `authStatus` (presence only), `listModels`,
  `listModelsWithAvailability`, `startSession` validation.
- Explicit failures for `resumeToken`, stdio MCP, multiple MCP servers,
  missing provider/credential/model.
- `provider` identity set on every discovered model.

Tests: capability matrix, discovery with/without provider, credential
presence only, model parsing, availability, explicit unsupported failures,
no secret in messages.

## Task 4 — Streaming session, tool loop, interrupt

Files: `src/engines/openai-compatible/session.ts`,
`tests/unit/openai-compatible-session.test.ts`.

Produces:

- Per-session history, pinned model, system instructions.
- Streaming text/thought/usage events.
- OpenAI tool-call loop through the MCP client, tool start/end events,
  bounded iterations, tool errors returned to the model.
- Interrupt -> aborted fetch and `result cancelled`; close idempotent.
- Truncated/filtered completions reported honestly as failure.

Tests: text stream, usage, one and multiple tool iterations, tool failure,
interrupt, close, max-iteration refusal, no duplicate tool side effects.

## Task 5 — Registry and non-process execution seam

Files: `src/engines/registry.ts`, `src/execution/adapter.ts`,
`tests/unit/engine-registry-provider.test.ts`.

Produces:

- `EngineFactory.spawnsProcess` (default true) and `engineSpawnsProcess()`.
- `openai-compatible` registration with `spawnsProcess: false`.
- `nativeAdapterFor` returns the adapter directly for non-process engines.
- Production discovery excludes `devOnly` mock (existing behaviour pinned).

Tests: factory metadata, no `prepare()` call for HTTP engines, mock excluded,
provider/rootDir forwarded through engine options.

## Task 6 — Config, routing and CLI wiring

Files: `src/config/schema.ts`, `src/cli/commands/provider.ts`,
`src/cli/main.ts`, `src/cli/commands/ship.ts`,
`src/orchestrator/service.ts`, `src/server/routes.ts`,
`src/cli/commands/chat.ts`, `src/cli/commands/doctor.ts`,
`tests/unit/ship-provider.test.ts`, `tests/integration/provider-cli.test.ts`.

Produces:

- Optional `ships.<id>.provider` in config (no DB migration).
- Provider resolution per Ship at every adapter construction site.
- `pluton provider list|add|key|remove-key|validate|models|remove`.
- `ship create/edit --provider`.
- `/api/models` and doctor use the configured provider.
- Provider failures are explicit; no silent model substitution.

Tests: config round-trip, ambiguous provider failure, CLI key never in argv or
output, ship create/edit persists provider, route/model discovery for one
provider, doctor auth check.

Verification: `npm run typecheck`, `npm run build`, focused tests, full
`npm test`, `npm run test:e2e`, `npm run verify:docs`, `npm run verify:assets`,

approval before Phase 2.

## Review focus

- Secrets in any surface (error text, JSON output, argv, SQLite, events).
- A provider failure silently erasing inventory or selecting another provider.
- Approval/resume capabilities claimed but not implemented.
- Tool-loop replay after interrupt.
- Provider-specific assumptions leaking into generic runtime code.
