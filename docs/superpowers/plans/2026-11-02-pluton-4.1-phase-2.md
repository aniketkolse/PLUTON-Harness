# PLUTON 4.1 Phase 2: Settings Provider & Model Selection UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the graphical workspace Settings Provider management interface, server REST endpoints, searchable model selection dialog, and atomic Ship model assignment so that Ships immediately run with their assigned provider and model.

**Architecture:** Extend the HTTP server (`src/server/routes.ts`) with `/api/providers` management endpoints calling the Phase 1 provider store. Enhance `/api/ships/:id/model` to atomically validate model compatibility, update `pluton.yaml` via `editShip`, update SQLite Ship records, and restart live engine sessions with the new provider and model. Upgrade the SPA embedded assets (`src/server/static-assets.ts`) to provide a Providers card in Settings and a searchable, filterable "Select Model" dialog.

**Tech Stack:** TypeScript, Node.js 24 (`node:http`, `node:sqlite`), vanilla HTML/CSS/JS in `src/server/static-assets.ts`, Vitest.

**Spec:** `docs/PLUTON_4.1_UPGRADE_AUDIT.md` (Sections 5 & 11) and `docs/superpowers/plans/2026-11-02-pluton-4.1-phase-1.md`.

## Global Constraints

- Never expose plaintext API keys in logs, errors, events, CLI output, or API responses; return `hasCredential: boolean` only.
- Store credentials exclusively in `.pluton/provider-homes/<id>/credential.json` (0600 on POSIX, restricted Windows SID ACLs).
- All changes must preserve asset verifier contracts (`scripts/verify-assets.mjs` element IDs and API calls must remain present and functional).
- Persist Ship model and provider assignments to `pluton.yaml` and restart live engine sessions so the Ship runs with the assigned model only.
- Strict backward compatibility: `/api/muses/<id>/model` remains an alias for `/api/ships/<id>/model`.
- Zero new external runtime dependencies.

## Review Focus

1. **Secret Leakage in Provider API**: `GET /api/providers` or `POST /api/providers` must never return the plaintext `apiKey`.
2. **Atomic Ship Update Failure**: Invalid model or non-existent provider must reject with 400 and leave `pluton.yaml` and the running session untouched.
3. **Session Reconnection on Switch**: Switching a Ship's model must terminate the old session and restart the engine session with the exact `(engine, provider, model)`.
4. **Asset Contract Preservation**: Embedded HTML template in `static-assets.ts` must maintain all IDs required by `scripts/verify-assets.mjs`.
5. **Offline/Discovery Failure Resilience**: If model discovery probe fails or endpoint is unreachable, validation errors must be surfaced clearly without crashing the server.

### Task 1: Provider Management REST API Endpoints

**Files:**
- Modify: `src/server/routes.ts`
- Test: `tests/server/provider-routes.test.ts`

**Interfaces:**
- Consumes: `listProviders`, `saveProvider`, `removeProvider`, `hasProviderCredential`, `writeProviderCredential`, `removeProviderCredential`, `getProvider` from `src/providers/store.ts`; `providerValidate` from `src/cli/commands/provider.ts`.
- Produces: HTTP routes:
  - `GET /api/providers`: returns `{ ok: true, providers: ProviderSummary[] }`
  - `POST /api/providers`: accepts provider configuration and optional `apiKey`; returns `{ ok: true, provider: ProviderConfig }`
  - `DELETE /api/providers/:id`: removes provider and credential home; returns `{ ok: true, removed: boolean }`
  - `POST /api/providers/:id/key`: accepts `{ apiKey: string }`; stores credential; returns `{ ok: true, configured: boolean }`
  - `DELETE /api/providers/:id/key`: deletes credential; returns `{ ok: true, removed: boolean }`
  - `POST /api/providers/:id/validate`: runs validation report; returns `{ ok: true, report: ProviderValidationReport }`

  - `DELETE /api/providers/:id/key` removes credential.
